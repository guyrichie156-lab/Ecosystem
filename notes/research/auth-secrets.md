## Главное
1. **Главный риск — подпись APK.** Файл `apps/mobile/android/app/debug.keystore` побайтно совпадает с ключом из публичных шаблонов Expo SDK 57 и React Native. Пароль `android` написан в шаблонном `build.gradle` (ссылки в разделе 1). Android ставит обновление поверх, если сертификат совпадает ([App signing](https://developer.android.com/studio/publish/app-signing)). Вывод из этих фактов: любой человек может собрать APK `com.ecosystem.mobile` с подписью, которую Android примет как обновление. Чтобы добраться до данных, этот APK ещё нужно установить на телефон пользователя. Для этого нужен разблокированный телефон в руках, согласие самого пользователя поставить «обновление» или подмена файла в ветке `apk` (нужно право push). Для установки из браузера или файлового менеджера у этого источника должно быть разрешение «Install unknown apps» ([Publish](https://developer.android.com/studio/publish)). Установленный так APK обходит любую блокировку и любое шифрование внутри приложения.
2. **Резервные копии.** Сейчас стоит `allowBackup="true"` без правил, поэтому база попадает в копию Google, если на телефоне включено резервное копирование и данных приложения не больше 25 МБ. Если их больше, система вызывает `onQuotaExceeded()` и в облако не копирует ничего, пока объём не уменьшится ([Auto Backup](https://developer.android.com/identity/data/autobackup)). Ловушка: если добавить `expo-secure-store` с настройками по умолчанию, его правила оставят в копии только shared preferences, и база перестанет копироваться (раздел 3.4).
3. **Нет блокировки и защиты экрана.** Суммы видны в «Недавних», на виджете и в тексте уведомлений о бюджете. На экране блокировки они могут быть видны: по умолчанию у уведомления уровень `VISIBILITY_PRIVATE` — на защищённом экране блокировки видны значок и заголовок, полный текст скрыт, но окончательно решают настройки телефона ([Notification#visibility](https://developer.android.com/reference/android/app/Notification#visibility)). Как настроен телефон пользователя — «Я не могу это подтвердить».
4. **Git чистый, но `.gitignore` неполный.** В истории секретов нет. При этом `*.keystore`, `.env.production`, `credentials.json`, `google-services.json` и `*.db` не игнорируются. В 4 коммитах публично виден личный адрес gmail.
5. **Рекомендация, порядок работ:** свой ключ подписи → правила копирования и зашифрованный экспорт → блокировка (биометрия или PIN телефона) и скрытие в «Недавних» → скрытые уведомления → SQLCipher по решению пользователя. Для облака сначала обойтись без аккаунта (зашифрованный файл), а настоящую синхронизацию делать только со сквозным шифрованием.

### 3.1 Ключ подписи
**Факты.**
- Обновление ставится, только если сертификат совпадает: «users can only update your app if the update is signed with the same signing key» ([App signing](https://developer.android.com/studio/publish/app-signing)).
- По той же странице: отладочный сертификат «insecure by design»; ключу рекомендуется срок не меньше 25 лет («should be valid for at least 25 years»), а для Google Play срок обязан заканчиваться после 22.10.2033; без Play App Signing потеря ключа означает, что обновлять приложение больше нельзя.
- Сборка debug по умолчанию отлаживаемая (`debuggable true`) и подписана общим отладочным ключом ([build variants](https://developer.android.com/build/build-variants)). С Android 12 `adb backup` не выгружает данные приложения, если оно не отлаживаемое ([Android 12](https://developer.android.com/about/versions/12/behavior-changes-12)). Значит, отладочную сборку, поставленную кабелем поверх release, можно выгрузить через adb.
- Ротация. `apksigner rotate` создаёт родословную ключей (lineage), `apksigner sign … --next-signer … --lineage` подписывает APK. На Android 13+ по умолчанию используется блок v3.1 ([apksigner](https://developer.android.com/tools/apksigner)).
- Возможность `--set-rollback` по умолчанию выключена: в `apksigner.jar` 36.0.0 флаги по умолчанию равны 23, а бит rollback — 8 (проверено через `javap`). Справка `apksigner rotate --help` предупреждает: с этим флагом «a compromised key could retake control of an app even after the signing certificate rotation». Справка также говорит, что lineage можно прочитать из уже подписанного APK.

**Рекомендация (порядок).**
1. Создать ключ: `keytool -genkeypair -v -storetype PKCS12 -keystore ecosystem-release.p12 -alias ecosystem -keyalg RSA -keysize 2048 -validity 10000` (команда из [RN signed APK](https://raw.githubusercontent.com/facebook/react-native-website/main/docs/signed-apk-android.md); 10000 дней ≈ 27 лет). Пароли и пароль хранилища не вставлять в чат.
2. Хранить: файл и пароли во вложении менеджера паролей плюс офлайн-копия (например, зашифрованная флешка). Никогда не класть в `apps/mobile/android/`: эту папку стирает `prebuild --clean` (CLAUDE.md).
3. Где подписывать — варианты:
   - (а) Облако Claude, **отдельное окружение «release»**. Переменные окружения видит любая команда в сессии, «Anyone who uses the environment can read the values» ([cloud environments](https://code.claude.com/docs/en/cloud-environments.md)). Network secrets подставляются только в HTTP-запросы, для файла ключа не подходят (Мнение).
   - (б) Компьютер пользователя: `~/.gradle/gradle.properties` ([RN](https://raw.githubusercontent.com/facebook/react-native-website/main/docs/signed-apk-android.md)).
   - (в) EAS Build: ключ хранится на серверах Expo ([managed credentials](https://raw.githubusercontent.com/expo/expo/main/docs/pages/app-signing/managed-credentials.mdx)); бесплатно 15 сборок Android в месяц ([pricing](https://expo.dev/pricing), по выдержке поиска).
   - (г) GitHub Actions: секреты, бинарный файл кладут как base64; при запуске из форка секреты не передаются ([use secrets](https://raw.githubusercontent.com/github/docs/main/content/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets.md), [forks](https://raw.githubusercontent.com/github/docs/main/data/reusables/actions/forked-secrets.md)).

   Мнение: (а) меньше всего меняет текущий процесс сборки.
4. Переход без потери данных — ротация. Gradle собирает как сейчас, затем APK переподписывается:
   ```bash
   apksigner rotate --out ecosystem.lineage --old-signer --ks debug.keystore --ks-pass pass:android \
     --new-signer --ks ecosystem-release.p12 --ks-pass env:ECO_KS_PASS      # один раз
   apksigner sign --ks debug.keystore --ks-pass pass:android --next-signer --ks ecosystem-release.p12 \
     --ks-pass env:ECO_KS_PASS --lineage ecosystem.lineage --out app-signed.apk app-release.apk
   apksigner verify -v --print-certs app-signed.apk
   ```
   Рекомендация: сначала отрепетировать на телефоне с пробным пакетом (в облаке эмулятора нет, `notes/architecture.md`). Перед ротацией сделать экспорт (П6).
5. Запасной путь: экспорт → удаление → установка → импорт. Мнение: разрешения Health Connect и виджет придётся настроить заново.
6. После перехода сборка `pnpm android` с отладочным ключом не встанет поверх, поэтому нужен П1б.

### 3.2 Блокировка приложения
**Факты (исходники expo-local-authentication в ветке `sdk-57`).**
- `authenticateAsync` показывает Android BiometricPrompt. Допускается выбранный класс биометрии, а также `DEVICE_CREDENTIAL` (PIN, графический ключ или пароль телефона), если не задано `disableDeviceFallback`. Если на телефоне нет защищённой блокировки экрана, возвращается ошибка `not_enrolled` ([модуль](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-local-authentication/android/src/main/java/expo/modules/localauthentication/LocalAuthenticationModule.kt)).
- `biometricsSecurityLevel` по умолчанию `'weak'`: подходит и Class 2, например распознавание лица по камере. `'strong'` разрешает только Class 3 ([типы](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-local-authentication/src/LocalAuthentication.types.ts)).
- Сочетание `BIOMETRIC_STRONG | DEVICE_CREDENTIAL` не поддерживается на Android 10 и ниже ([biometric auth](https://developer.android.com/identity/sign-in/biometric-auth)). Для Android 14 это не важно.
- Результат — просто `{success: true}`, он не привязан к криптографии. OWASP пишет, что такую проверку легко обойти, если процесс аутентификации не возвращает данных ([MASTG](https://raw.githubusercontent.com/OWASP/mastg/master/Document/0x05f-Testing-Local-Authentication.md)). Мнение: это ширма от посторонних глаз, а не защита данных.
- Опция `requireAuthentication` в SecureStore требует биометрию Class 3, в окне есть только кнопка «Отмена» (PIN не предлагается). При изменении биометрии, например при добавлении отпечатка, данные становятся недоступны ([AuthenticationHelper](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-secure-store/android/src/main/java/expo/modules/securestore/AuthenticationHelper.kt), [AuthenticationPrompt](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-secure-store/android/src/main/java/expo/modules/securestore/AuthenticationPrompt.kt), [SecureStore](https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/v57.0.0/sdk/securestore.mdx)).
- На Android `AppState` переходит в `background` и тогда, когда открыта временная системная activity ([AppState](https://raw.githubusercontent.com/facebook/react-native-website/main/docs/appstate.md)).
- Как сделано у других:
  - Monzo, App Lock: PIN или биометрия при каждом запуске, если проверки не было в последние 5 минут ([Monzo](https://monzo.com/help/Account%20Security/AppLockFAQS), по выдержке поиска).
  - Revolut: биометрия открывает приложение и подтверждает платежи ([Revolut](https://help.revolut.com/help/profile-and-plan/log-in-issues/sign-in-with-face-id-or-fingerprint/), по выдержке поиска).
  - Money Manager (Realbyte): код из 4 цифр, включаемая биометрия, частота запроса настраивается ([Realbyte](https://help.realbyteapps.com/hc/en-us/articles/360043501233-Passcode-guide), по выдержке поиска).

**Рекомендация.**
- Своего PIN не заводить, запасным способом брать PIN телефона: не нужно хранить секрет и считать попытки.
- `biometricsSecurityLevel: 'strong'`.
- Блокировать при холодном старте и после N минут в фоне. Время ухода в фон держать в памяти. Порог N защищает от ложной блокировки, когда открыты окно ввода PIN, Health Connect или «Поделиться».
- Компонент `AppLockGate` в `packages/core`, монтируется в корневом layout. Миграции и `prepare` идут под заставкой, так что старт не замедляется. Мнение: это исключение из правила CLAUDE.md «ничего в корневом layout», его надо записать в решения.
- Ссылки `ecosystem://` открывают экран только под заставкой.
- В веб-версии блокировки нет: модуль поддерживает только Android и iOS ([docs](https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/v57.0.0/sdk/local-authentication.mdx)), нужна заглушка `.web.ts`.
- Альтернатива без кода на Android 15+: «Private space». Это отдельный профиль, при блокировке скрыт из «Недавних» и уведомлений ([Android 15](https://developer.android.com/about/versions/15/features#private-space)). Данные там будут отдельной установкой; работа виджета и Health Connect в нём — «Я не могу это подтвердить».

### 3.3 «Недавние» и скриншоты
**Факты.**
- `preventScreenCaptureAsync()` на Android добавляет окну `FLAG_SECURE` ([модуль](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-screen-capture/android/src/main/java/expo/modules/screencapture/ScreenCaptureModule.kt)). Это запрещает скриншоты, запись и показ на незащищённых экранах, а превью в «Недавних» становится пустым ([ScreenCapture.ts](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-screen-capture/src/ScreenCapture.ts), [FLAG_SECURE](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#FLAG_SECURE)).
- `enableAppSwitcherProtectionAsync` работает только на iOS.
- `Activity.setRecentsScreenshotEnabled(false)` (API 33+) прячет только превью в «Недавних», а скриншоты, сделанные самим пользователем, продолжают работать ([Activity](https://developer.android.com/reference/android/app/Activity#setRecentsScreenshotEnabled(boolean))). В expo-screen-capture этого вызова нет.

**Мнение:** пользователь присылает скриншоты для доработки дизайна, поэтому вариант Б удобнее. Выбор — вопрос пользователю.

### 3.4 Резервные копии Android
**Факты.**
- В Expo есть только ключ `android.allowBackup` (`@expo/config-types` 57.0.2, `@expo/config-plugins` 57.0.7, `AllowBackup.js`). Готовых ключей для `dataExtractionRules` и `fullBackupContent` в `@expo/config-plugins` и `@expo/prebuild-config` я не нашёл.
- У плагина `expo-secure-store` параметр `configureAndroidBackup` по умолчанию равен `true` ([плагин](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-secure-store/plugin/src/withSecureStore.ts)). Он подключает свои правила `<include domain="sharedpref" path="."/>` + `<exclude … path="SecureStore"/>` ([XML](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-secure-store/android/src/main/res/xml/secure_store_data_extraction_rules.xml)).
- Android: «If you specify an `<include>` element, the system no longer includes any files by default» ([Auto Backup](https://developer.android.com/identity/data/autobackup)). Значит, после добавления SecureStore база выпадет и из облачной копии, и из переноса на новый телефон.
- Значения SecureStore после восстановления не расшифровать: ключи Keystore удаляются вместе с приложением ([SecureStore](https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/v57.0.0/sdk/securestore.mdx)).
- Для домена `sharedpref` Android сам добавляет к пути `.xml`, поэтому `path="SecureStore"` корректен ([FullBackup.java](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/app/backup/FullBackup.java)).

**Рекомендация.** Оставить `allowBackup: true`, у плагина SecureStore поставить `configureAndroidBackup: false`, а свои правила писать через П5:
```xml
<!-- res/xml/data_extraction_rules.xml, Android 12+ -->
<data-extraction-rules>
  <cloud-backup disableIfNoEncryptionCapabilities="true">
    <exclude domain="sharedpref" path="SecureStore"/>
    <!-- только если включён SQLCipher (П7): <exclude domain="file" path="SQLite/"/> -->
  </cloud-backup>
  <device-transfer>
    <exclude domain="sharedpref" path="SecureStore"/>
  </device-transfer>
</data-extraction-rules>
<!-- res/xml/backup_rules.xml, Android 11 и ниже: <full-backup-content> с тем же exclude -->
```
`disableIfNoEncryptionCapabilities` отправляет копию в облако, только если её можно зашифровать, то есть если на телефоне есть блокировка экрана ([Auto Backup](https://developer.android.com/identity/data/autobackup)). Восстановит ли Android копию в приложение с новым ключом подписи — «Я не могу это подтвердить». Поэтому опираться стоит на П6.

### 3.5 Данные в покое: SQLCipher (П7)
**Факты.**
- `useSQLCipher` — параметр плагина `expo-sqlite`, по умолчанию `false`. Поддерживаются Android, iOS и macOS; Expo Go не поддерживается. `PRAGMA key` выполняется сразу после открытия базы ([expo-sqlite v57](https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/v57.0.0/sdk/sqlite.mdx)).
- Установленный пакет собирает `vendor/sqlcipher` (SQLCipher 4.7.0 на SQLite 3.49.1; обычная сборка — SQLite 3.50.3) с OpenSSL `io.github.ronickg:openssl:3.3.2-1` (`node_modules/expo-sqlite/android/build.gradle`, `vendor/*/sqlite3.c`).
- Из [README SQLCipher](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/README.md):
  - ключ из 64 hex-символов используется напрямую, без выработки ключа (KDF);
  - `PRAGMA rekey` меняет ключ у уже зашифрованной базы;
  - без ключа SQLCipher работает как обычный SQLite;
  - открытую базу шифруют через `ATTACH` и `sqlcipher_export()`;
  - накладные расходы — «as little as 5-15% overhead… on many operations» (оценка производителя).
- По [Zetetic](https://www.zetetic.net/sqlcipher/encrypting-plaintext-databases/) (по выдержке поиска): после экспорта открытый файл нужно удалить, а `rekey` не подходит для шифрования открытой базы. По [SQLCipher 4.0](https://www.zetetic.net/blog/2018/11/30/sqlcipher-400-release/) (по выдержке поиска): ключ из пароля вырабатывается через PBKDF2-HMAC-SHA512 с 256 000 итераций.
- Ключ:
  - `getRandomBytes` в expo-crypto использует `SecureRandom` ([CryptoModule.kt](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-crypto/android/src/main/java/expo/modules/crypto/CryptoModule.kt)). В `__DEV__` при удалённой отладке есть запасной вариант через `Math.random` ([Crypto.ts](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-crypto/src/Crypto.ts)).
  - SecureStore шифрует значения ключом AES-256-GCM из Keystore ([AESEncryptor.kt](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-secure-store/android/src/main/java/expo/modules/securestore/encryptors/AESEncryptor.kt)). У него есть синхронные `getItem` и `setItem` ([SecureStore.ts](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-secure-store/src/SecureStore.ts)), но нет веб-версии. При удалении приложения его данные теряются ([docs](https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/v57.0.0/sdk/securestore.mdx)).
- Keystore: если процесс приложения захвачен, ключом можно пользоваться, но извлечь его нельзя ([Keystore](https://developer.android.com/privacy-and-security/keystore)). Вывод: подменённый APK с тем же ключом подписи (угроза 7) прочитает и зашифрованную базу.

**Рекомендация (как сделать).**
- 32 байта из `getRandomBytesAsync` → hex → `SecureStore.setItem` **без** `requireAuthentication`: иначе не сработают виджет и фоновые задачи, а при смене биометрии данные потеряются.
- В `packages/db/src/client.ts` сразу после `openDatabaseSync` выполнять `execSync(\`PRAGMA key = "x'…'"\`)`. Задача виджета берёт этот же клиент (`app-entry.js` → `registerFinanceWidgetTaskHandler`), так что ключ будет и там.
- Миграция при первом запуске: `PRAGMA wal_checkpoint(TRUNCATE)` → `ATTACH 'ecosystem.enc.db' AS enc KEY "x'…'"` → `SELECT sqlcipher_export('enc')` → `DETACH` → проверить число строк → заменить файл и удалить открытую копию.
- Веб остаётся без шифрования: SQLCipher и SecureStore там не поддерживаются, нужна ветка `client.web.ts`.
- Скорость на телефоне — «Я не могу это подтвердить». План замера: время до первого экрана, «Записи» и «Отчёты» по 3 раза до и после; размер APK, сейчас 62,7 МБ (`notes/architecture.md`).

**Мнение.** Делать после П1–П6. SQLCipher защищает файл, если его извлекли (копии, криминалистика на разблокированном телефоне), но не защищает от подменённого APK и от root на самом телефоне.

### 3.6 Health Connect
**Факты.**

На Android 14+ её открывают через activity-alias `VIEW_PERMISSION_USAGE`. Это должна быть та же политика, что указана в Play Console ([get started](https://developer.android.com/health-and-fitness/health-connect/get-started)).

**Рекомендация (П9).** Короткий экран на русском: какие данные читаются, что они не покидают телефон, как их удалить. Этот же текст пригодится как политика для Play.

## 4. «При облачной синхронизации»

| Вариант | Суть | Мнение |
|---|---|---|
| 0. Без аккаунта | П6: зашифрованный файл сохраняется через «Поделиться» или выбор файла | **Минимальный путь**: нет сервера, токенов и аккаунта |
| 1. Supabase Auth + Postgres | Почта, magic link, OAuth; SDK сам обновляет токены ([Expo auth guide](https://raw.githubusercontent.com/expo/expo/main/docs/pages/develop/authentication.mdx)) | Если нужна настоящая синхронизация, то этот вариант, но только со сквозным шифрованием |
| 2. Firebase Auth | Через `react-native-firebase` в development build (там же) | Равноценная альтернатива |
| 3. Свой бэкенд + passkeys | `react-native-passkeys` или Clerk (там же) | Больше всего работы |
| Вход через Google | Старый Google Sign-In SDK устарел, Google советует Credential Manager ([migration](https://developer.android.com/identity/sign-in/legacy-gsi-migration)). У `@react-native-google-signin` Credential Manager есть только в платной версии, у `react-native-nitro-google-signin` — в обычной ([Expo](https://raw.githubusercontent.com/expo/expo/main/docs/pages/guides/google-authentication.mdx)). Для доступа к Google Диску нужен `AuthorizationClient` ([SIWG](https://developer.android.com/identity/sign-in/credential-manager-siwg)) | Хорошо сочетается с 1 или 2 |

**Факты для реализации.**
- OAuth в нативных приложениях выполняется во внешнем браузере, а не во встроенном WebView (RFC 8252, [rfc-editor](https://www.rfc-editor.org/rfc/rfc8252), по выдержке поиска). AppAuth следует RFC 8252, использует Custom Tabs, «WebView is explicitly *not* supported» и поддерживает PKCE ([AppAuth-Android](https://raw.githubusercontent.com/openid/AppAuth-Android/master/README.md)).
- В expo-auth-session (ветка `sdk-57`, 57.0.16) по умолчанию `usePKCE: true` и `S256`; метод `Plain` отклоняется как небезопасный ([AuthRequest.ts](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-auth-session/src/AuthRequest.ts)). Текст RFC 7636 я не открывал: rfc-editor закрыт прокси.
- «Never put any secret keys inside your application code» ([auth-session](https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/v57.0.0/sdk/auth-session.mdx)).
- Supabase:
  - в общем случае refresh-токен одноразовый. Исключения: повтор в течение интервала (по умолчанию 10 секунд, менять не рекомендуется) и использование родительского токена текущего активного — тогда сервер возвращает активный токен. Любой другой повтор завершает сессию и отзывает все её refresh-токены. Эту защиту можно отключить в настройках Auth, но так делать не рекомендуется. От кражи сессии с самого устройства это не защищает ([sessions](https://raw.githubusercontent.com/supabase/supabase/master/apps/docs/content/guides/auth/sessions.mdx));
  - RLS нужно включить на каждой открытой таблице ([RLS](https://raw.githubusercontent.com/supabase/supabase/master/apps/docs/content/guides/database/postgres/row-level-security.mdx));
  - руководство Expo хранит сессию в `expo-sqlite/localStorage`, то есть без шифрования ([guide](https://raw.githubusercontent.com/expo/expo/main/docs/pages/guides/using-supabase.mdx)). Руководство Supabase предлагает «LargeSecureStore»: ключ AES лежит в SecureStore, а зашифрованная сессия — рядом ([tutorial](https://raw.githubusercontent.com/supabase/supabase/master/apps/docs/content/guides/getting-started/tutorials/with-expo-react-native.mdx)).
- В expo-crypto 57 есть AES-GCM (128/192/256), но нет функций выработки ключа из пароля (PBKDF2, Argon2) — так по списку экспортов ([Crypto.ts](https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-crypto/src/Crypto.ts), [crypto docs](https://raw.githubusercontent.com/expo/expo/main/docs/pages/versions/v57.0.0/sdk/crypto.mdx)).
- Если подключить EAS Update, аккаунт Expo станет частью цепочки доверия. Подпись обновлений доступна только на планах Production и Enterprise ([code signing](https://raw.githubusercontent.com/expo/expo/main/docs/pages/eas-update/code-signing.mdx)).

**Рекомендация (схема сквозного шифрования).**
- Ключ данных (DEK, 256 бит, `getRandomBytes`) хранится в SecureStore. Перед отправкой данные шифруются AES-256-GCM.
- DEK дополнительно шифруется **ключом восстановления**: 256 случайных бит, показываются один раз текстом или QR-кодом для менеджера паролей. KDF при этом не нужен.
- Сервер видит только шифротекст, размеры и время. Токены хранятся в SecureStore или по схеме LargeSecureStore. Если потерять и телефон, и ключ восстановления, данные пропадут — это свойство схемы.

- GDPR, ст. 9(1): данные о здоровье — особая категория ([legislation.gov.uk](https://www.legislation.gov.uk/eur/2016/679/article/9/adopted), по выдержке поиска).
- GDPR, ст. 2(2)(c): регламент не применяется к сугубо личной или домашней деятельности ([gdpr-text.com](https://gdpr-text.com/en/read/article-2/), вторичный источник, по выдержке поиска).
- Беларусь: Закон № 99-З от 07.05.2021 «О защите персональных данных» ([neg.by](https://neg.by/novosti/otkrytj/personalnye-dannye-pravila-obrabotki-i-ispolzovaniya), по выдержке поиска). Данные о здоровье отнесены к «специальным персональным данным», по ссылке на абз. 12 ст. 1 во вторичном источнике ([nalog-nalog.ru](https://nalog-nalog.ru/dontknows/chto-otnositsya-k-specialnym-kategoriyam-personalnyh-dannyh/), по выдержке поиска). Есть ли там исключение для личного использования — «Я не могу это подтвердить».
- Мнение: со сквозным шифрованием провайдер облака данных о здоровье не видит. Если приложение когда-нибудь получит других пользователей, понадобятся политика конфиденциальности, согласие и юридическая проверка.

## 5. «Если публиковать в Google Play» и установка вне Play
- **Play App Signing** обязателен: отказаться можно только для приложений, созданных до августа 2021. Чтобы APK из Play и APK вне Play совпадали по подписи, Google нужно передать свой ключ («provide your own signing key»). Upload-ключ можно сбросить. Ключ должен действовать после 22.10.2033. Приложение с отладочной подписью Play не примет ([App signing](https://developer.android.com/studio/publish/app-signing)).
- **Health Connect:** раздел 3.6.
- **Проверка разработчиков** ([verification](https://developer.android.com/developer-verification), [FAQ](https://developer.android.com/developer-verification/guides/faq), [limited distribution](https://developer.android.com/developer-verification/guides/limited-distribution)):
  - с 30.09.2026 — только Бразилия, Индонезия, Сингапур и Таиланд и только для установок из участвующих магазинов; ручная установка APK пока не затронута; во всём мире — в 2027;
  - установка через `adb` не требует проверки;
  - аккаунт «limited distribution» бесплатный, до 20 устройств, без документов, но с 2-Step Verification и платёжным профилем Google;
  - «If you lose your signing key you won't be able to register your packages»; если имя пакета уже используется, ключ могут признать «not eligible to claim it outright»: Google советует взять другое имя, а запрос на занятое пройдёт дополнительную проверку, и этим именем смогут пользоваться и другие разработчики;
  - опытный пользователь может включить «advanced flow» с суточным ожиданием.
- Мнение: это ещё один повод завести свой ключ сейчас. Удастся ли зарегистрировать `com.ecosystem.mobile` с публичным отладочным ключом и доступен ли аккаунт разработчика из Беларуси — «Я не могу это подтвердить».

## 6. Секреты: правила проекта (готово для вставки в notes)
- [ ] Репозиторий публичный. В Git не попадают ключи, пароли, токены, `.env` с настоящими значениями, база (`*.db`), файлы экспорта, скриншоты с реальными суммами и замерами, реальные суммы в тестах и заметках.
- [ ] Ключ подписи релиза и его пароли хранятся только в менеджере паролей пользователя и в офлайн-копии. Никогда — в Git, в заметках, в чате с Claude или в `apps/mobile/android/` (её стирает `prebuild --clean`).
- [ ] Пароли не вставлять в чат. В облачную сборку они попадают только через переменные отдельного окружения «release»: их видит любая команда в сессиях этого окружения.
- [ ] `EXPO_PUBLIC_*` — не секрет, значение попадает в бандл открытым текстом ([env vars](https://raw.githubusercontent.com/expo/expo/main/docs/pages/guides/environment-variables.mdx)). Переменные EAS с видимостью «secret» тоже не защищают значение, если оно попадает в приложение ([EAS env](https://raw.githubusercontent.com/expo/expo/main/docs/pages/eas/environment-variables/index.mdx)).
- [ ] Ключ шифрования базы и копий создаётся на телефоне (expo-crypto), хранится в SecureStore без `requireAuthentication`, не логируется и не экспортируется. Ключ восстановления знает только пользователь.
- [ ] В логах release нет сумм, заметок и замеров. Ошибки базы пишутся без `params`.
- [ ] Перед коммитом смотреть `git status` и diff. Push protection — страховка, а не гарантия.
- [ ] Если секрет попал в Git, он скомпрометирован: сначала сменить ключ или пароль, чистка истории вторична ([GitHub](https://raw.githubusercontent.com/github/docs/main/content/code-security/concepts/secret-security/secret-scanning.md)).
- [ ] Коммиты — с адресом noreply. GitHub и claude.ai (и Expo, если появится) — с 2FA или passkey ([2FA](https://raw.githubusercontent.com/github/docs/main/content/authentication/securing-your-account-with-two-factor-authentication-2fa/about-two-factor-authentication.md)).
- [ ] Добавить в `.gitignore` корня: `.env*` (кроме `!.env.example`), `*.jks`, `*.keystore`, `*.p12`, `*.p8`, `*.pem`, `*.key`, `keystore.properties`, `credentials.json`, `google-services.json`, `GoogleService-Info.plist`, `*.db`, `*.db-wal`, `*.db-shm`, `*.sqlite`, файлы экспорта приложения, `*.hprof`.
- [ ] Рядом с каждым APK в ветке `apk` публиковать SHA-256 файла и SHA-256 сертификата.
